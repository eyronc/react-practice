01 useState — All the Ways to Use It hook ▼

useState lets React remember a value between renders. Every time you call the setter, React re-renders the component with the new value. Here are all the ways you'll see it written.

// The most basic form — you might see this first
import { useState } from 'react';

function Counter() {
  // useState returns an array: [currentValue, setterFunction]
  const countState = useState(0);
  const count = countState[0];         // get value
  const setCount = countState[1];      // set value

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>+</button>
    </div>
  );
}
// Type 2 — Array destructuring (the standard way everyone writes it)
import { useState } from 'react';

function Counter() {
  // Destructure directly — this is what you'll see 99% of the time
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>+</button>
      <button onClick={() => setCount(count - 1)}>-</button>
      <button onClick={() => setCount(0)}>Reset</button>
    </div>
  );
}
// Type 3 — Lazy initializer (for expensive initial values)
import { useState } from 'react';

function getInitialCount() {
  // Imagine this reads from localStorage or does heavy work
  return parseInt(localStorage.getItem('count')) || 0;
}

function Counter() {
  // Pass a FUNCTION, not a value — React only calls it once
  const [count, setCount] = useState(getInitialCount);
  //                                     ↑ no () — pass the fn itself

  return <p>Count: {count}</p>;
}
⚡ Why this matters

If you write useState(getInitialCount()) with parentheses, the function runs on EVERY render — wasteful. Without parentheses, React only runs it once on mount.

// Type 4 — Object state (group related values together)
import { useState } from 'react';

function UserForm() {
  const [user, setUser] = useState({
    name: '',
    age: 0,
    city: '',
  });

  // CRITICAL: Always spread the old state when updating object state
  const updateName = (e) => {
    setUser({ ...user, name: e.target.value });
    //        ↑ keep old fields, only change name
  };

  return (
    <div>
      <input value={user.name} onChange={updateName} />
      <p>Hello, {user.name || 'stranger'}!</p>
    </div>
  );
}
🧪 Experiment
  • Start with Type 2 (destructuring) — it's the standard. Get comfortable with it first.
  • Try calling setCount(count + 1) three times in a row inside one click handler. Does count go up by 3? (It won't. Learn why.)
  • Try setting state to the same value twice. Does React re-render? Check with a console.log.
02 The Functional Updater — setState(prev => ...) hook ▼

There are two ways to update state. The version you already know, and a safer version that uses the previous value. This matters more than it looks.

❌ Direct update (can be stale)

const [count, setCount] = useState(0);

// This reads count at the time of click
// If React batches updates, count may be stale
setCount(count + 1);
setCount(count + 1); // still +1, not +2!

✅ Functional updater (always safe)

const [count, setCount] = useState(0);

// prev is guaranteed to be the latest value
setCount(prev => prev + 1);
setCount(prev => prev + 1); // correctly +2!
// Real example — toggle with functional updater
const [isOn, setIsOn] = useState(false);

// Type A — direct (fine for simple toggles)
<button onClick={() => setIsOn(!isOn)}>Toggle</button>

// Type B — functional (preferred, always reads latest)
<button onClick={() => setIsOn(prev => !prev)}>Toggle</button>
💡 Rule of thumb

If your new state depends on the old state, always use prev => .... If it's a totally new value (like from an input), you can set directly.

🧪 Experiment
  • Make a button that calls setCount(count + 1) three times. What happens?
  • Now make it call setCount(prev => prev + 1) three times. What happens now?
  • This is called "state batching." You just discovered one of React's most common bugs.
03 Event Handlers — All the Ways to Write Them event ▼

React uses camelCase event names. You pass a function, never a function call. Here are all the styles you'll encounter — they all do the same thing, just written differently.

// Inline arrow — simple, great for one-liners
<button onClick={() => setCount(count + 1)}>Click</button>
<button onClick={() => setIsOpen(true)}>Open</button>
<input onChange={(e) => setValue(e.target.value)} />
// Named handler — cleaner when logic is more than one line
function App() {
  const [count, setCount] = useState(0);

  // Define the handler as a function inside the component
  const handleClick = () => {
    setCount(prev => prev + 1);
    console.log('clicked!');
  };

  // Pass the function REFERENCE — no () at the end!
  return <button onClick={handleClick}>Click</button>;
  //                          ↑ no parentheses here!
}
// With the event object — access e.target, e.preventDefault(), etc.
function App() {
  const [value, setValue] = useState('');

  // e is the event object — same as vanilla JS
  const handleChange = (e) => {
    setValue(e.target.value);   // what the user typed
    setValue(e.target.checked); // for checkboxes
    e.preventDefault();          // stop default behavior
    e.stopPropagation();         // stop event bubbling
  };

  return <input onChange={handleChange} value={value} />;
}
// Passing arguments — wrap in arrow function
function App() {
  const [selected, setSelected] = useState(null);

  const handleSelect = (id) => {
    setSelected(id);
  };

  return (
    <>
      // Wrap in arrow so it doesn't auto-call on render
      <button onClick={() => handleSelect(1)}>Select 1</button>
      <button onClick={() => handleSelect(2)}>Select 2</button>
      <p>Selected: {selected}</p>
    </>
  );
}
⚡ Common Mistake

onClick={handleSelect(1)} — this CALLS the function immediately when the component renders, not on click. Always wrap with an arrow: onClick={() => handleSelect(1)}

🧪 Experiment
  • Try onClick={handleClick()} with the parentheses. Notice it fires on render, not on click.
  • Add console.log(e) inside an onChange handler. Explore all the properties on the event object.
  • Try onDoubleClick, onMouseEnter, onKeyDown. React has an event for everything.
04 Controlled Inputs — React Owns the Value pattern ▼

In React, form inputs should be "controlled" — meaning React state drives the input's value, not the DOM. This gives you full control over what's in the field at all times.

❌ Uncontrolled (DOM owns value)

// React doesn't know what's in here
<input type="text" />

✅ Controlled (React owns value)

const [name, setName] = useState('');

<input
  value={name}
  onChange={(e) => setName(e.target.value)}
/>
// All controlled input types
function FormExample() {
  const [text, setText]         = useState('');
  const [checked, setChecked]   = useState(false);
  const [selected, setSelected] = useState('option1');
  const [area, setArea]         = useState('');

  return (
    <div>
      // Text input
      <input value={text} onChange={(e) => setText(e.target.value)} />

      // Checkbox — use e.target.checked, not e.target.value
      <input type="checkbox"
        checked={checked}
        onChange={(e) => setChecked(e.target.checked)} />

      // Select dropdown
      <select value={selected} onChange={(e) => setSelected(e.target.value)}>
        <option value="option1">Option 1</option>
        <option value="option2">Option 2</option>
      </select>

      // Textarea
      <textarea value={area} onChange={(e) => setArea(e.target.value)} />
    </div>
  );
}
🧪 Experiment
  • Add a <p> below each input that mirrors what you type in real-time. This is the power of controlled inputs.
  • Remove the onChange but keep value={text}. Try typing. What happens and why?
  • Try making an input that only allows numbers: onChange={(e) => setVal(e.target.value.replace(/\D/g, ''))}
05 Conditional Rendering — Show & Hide Things concept ▼

Show different UI based on state. There are four patterns — each has a use case. Learn all of them.

// Ternary — when you want to show one thing OR another
const [isLoggedIn, setIsLoggedIn] = useState(false);

return (
  <div>
    {isLoggedIn ? (
      <p>Welcome back!</p>
    ) : (
      <p>Please log in.</p>
    )}

    // Short inline version
    <h1>{isLoggedIn ? 'Dashboard' : 'Login'}</h1>
  </div>
);
// && operator — show something OR nothing
const [hasError, setHasError] = useState(false);
const [count, setCount]     = useState(5);

return (
  <div>
    // Only renders the p tag if hasError is true
    {hasError && <p>Something went wrong!</p>}

    // ⚠️ Gotcha: 0 && <p>...</p> renders "0" not nothing!
    {count && <p>Items: {count}</p>}  // Bug if count = 0

    // Fix: convert to boolean first
    {count > 0 && <p>Items: {count}</p>}
  </div>
);
// Early return — best for loading/error states
function UserProfile({ user }) {
  // Return early if no user — component stops here
  if (!user) {
    return <p>Loading...</p>;
  }

  if (user.banned) {
    return <p>Account suspended.</p>;
  }

  // Only reaches here if user exists and isn't banned
  return <h1>Hello, {user.name}!</h1>;
}
// Variable — for complex conditions, prep outside JSX
function StatusBadge({ status }) {
  // Decide what to render before the return
  let badge;
  if (status === 'active')  badge = <span>🟢 Active</span>;
  if (status === 'pending') badge = <span>🟡 Pending</span>;
  if (status === 'banned')  badge = <span>🔴 Banned</span>;

  return <div>Status: {badge}</div>;
}
🧪 Experiment
  • Build a toggle button that shows/hides a message. Use the ternary method first, then rewrite with &&.
  • Try the 0 && bug intentionally. Set count to 0 and watch "0" appear in your UI.
  • Build a StatusBadge component using the variable method with all 3 statuses.
06 Array State — Add, Remove, Update Items hook ▼

When state is an array, you never mutate it directly. Always create a new array. React won't re-render if you mutate in place.

// All the operations you'll need
const [items, setItems] = useState(['Apple', 'Banana']);

// ➕ ADD — spread old array + new item
const addItem = () => {
  setItems([...items, 'Cherry']);
  // or at the start:
  setItems(['Cherry', ...items]);
};

// ➖ REMOVE — filter out the item
const removeItem = (indexToRemove) => {
  setItems(items.filter((_, i) => i !== indexToRemove));
};

// ✏️ UPDATE — map and replace matching item
const updateItem = (index, newValue) => {
  setItems(items.map((item, i) =>
    i === index ? newValue : item
  ));
};

❌ Mutating (React won't re-render)

items.push('Cherry');  // BAD
items[0] = 'Mango';    // BAD
setItems(items);       // same ref!

✅ New array (React re-renders)

setItems([...items, 'Cherry']); // GOOD
setItems(items.map((x,i) =>   // GOOD
  i===0 ? 'Mango' : x));

07 Lifting State Up — Sharing Between Components pattern ▼

When two sibling components need the same data, move the state UP to their closest common parent and pass it down as props. This is one of React's most important patterns.

❌ Problem — both components have their own isolated state
function Search() {
  const [query, setQuery] = useState(''); // isolated!
  return <input onChange={(e) => setQuery(e.target.value)} />;
}

function Results() {
  // Can't see query from Search — different component!
  return <p>No access to query here</p>;
}
✅ Lifted — parent owns the state, passes it down
function Search({ query, onSearch }) {
  return (
    <input
      value={query}
      onChange={(e) => onSearch(e.target.value)}
    />
  );
}

function Results({ query }) {
  return <p>Searching for: {query}</p>;
}

// Parent owns the state — passes it to both children
function App() {
  const [query, setQuery] = useState('');

  return (
    <>
      <Search query={query} onSearch={setQuery} />
      <Results query={query} />
    </>
  );
}

08 Derived State — Compute, Don't Store concept ▼

Not everything needs to be in state. If a value can be calculated from existing state, just calculate it during render. Storing it in state is redundant and creates sync bugs.

❌ Redundant state (can get out of sync)

const [items, setItems]   = useState([]);
const [count, setCount]   = useState(0); // 👎

// Now you have to keep count in sync manually
const addItem = () => {
  setItems([...items, 'new']);
  setCount(count + 1); // easy to forget!
};

✅ Derived (always in sync)

const [items, setItems] = useState([]);

// Calculated from items — always correct
const count = items.length; // 👍

const addItem = () => {
  setItems([...items, 'new']);
  // count auto-updates. done.
};
// Practical derived state — Student Directory
function App() {
  const [students, setStudents] = useState([...]);
  const [query, setQuery]       = useState('');

  // These are derived — computed every render, never stored
  const filtered = students.filter(s =>
    s.name.toLowerCase().includes(query.toLowerCase())
  );

  const average = filtered.reduce((sum, s) =>
    sum + s.grade, 0) / filtered.length || 0;

  return (
    <>
      <input onChange={(e) => setQuery(e.target.value)} />
      <p>Showing {filtered.length} students, avg: {average.toFixed(1)}</p>
      {filtered.map(s => <StudentCard key={s.id} {...s} />)}
    </>
  );
}
💡 The Rule

Ask: "Can I compute this from existing state?" If yes — don't store it. Just calculate it in the render. This keeps your state minimal and always in sync.
