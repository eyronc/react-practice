01 What is useEffect? — Running Code After Render hook ▼

useEffect lets you run code after React renders your component. Use it for anything that reaches outside React — fetching data, setting up timers, manually touching the DOM, subscribing to events.

// The anatomy of useEffect
import { useState, useEffect } from 'react';

function App() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    // 1. This runs AFTER the component renders
    console.log('Component rendered! Count is:', count);

    // 2. Optionally return a cleanup function
    return () => {
      console.log('Cleaning up...');
    };
  }, [count]); // 3. Dependency array — when to re-run

  return <button onClick={() => setCount(c => c + 1)}>Count: {count}</button>;
}
💡 Mental model

Think of useEffect as: "After React paints the screen, then do this side effect." It's React's way of staying in control of the render cycle while still letting you interact with the outside world.

// All 3 forms — based on the dependency array
// Form 1: Runs after EVERY render
useEffect(() => {
  console.log('runs every render');
}); // ← no array at all

// Form 2: Runs ONCE on mount only
useEffect(() => {
  console.log('runs once on mount');
}, []); // ← empty array

// Form 3: Runs when specific values change
useEffect(() => {
  console.log('runs when userId changes');
}, [userId]); // ← array with dependencies

  • Add [] as the second arg. Click the button again. What changes?
  • Add a state variable to the array. When does the effect run now?
02 The Dependency Array — Controlling When Effects Run hook ▼

The dependency array is the most important part of useEffect. It tells React: "Only re-run this effect if one of these values changed since last render."

useEffect(fn) → Runs after every render
useEffect(fn, []) → Runs once on mount only
useEffect(fn, [a]) → Runs on mount + when a changes
useEffect(fn, [a,b]) → Runs on mount + when a OR b changes
// Practical example — sync document title with state
function App() {
  const [name, setName] = useState('');
  const [count, setCount] = useState(0);

  // Only runs when name changes
  useEffect(() => {
    document.title = `Hello, ${name}!`;
  }, [name]);

  // Only runs when count changes
  useEffect(() => {
    document.title = `Count: ${count}`;
  }, [count]);

  // You can have multiple useEffects in one component!
}
⚠️ The Golden Rule

Every value from your component that you use inside the effect MUST be in the dependency array. If you read userId inside the effect, it goes in the array. Missing dependencies = stale data bugs.

🧪 Experiment
  • Use useEffect to update document.title whenever a search input changes.
  • Try two separate useEffect calls — one for each piece of state. They run independently.
  • Intentionally leave a dependency OUT of the array. Notice the stale value bug.
03 Cleanup — Preventing Memory Leaks concept ▼

When your effect sets up something ongoing — a timer, an event listener, a WebSocket — you must clean it up when the component unmounts, or you'll leak memory and cause bugs.

// Setting up and clearing an interval
function Timer() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    // Start the interval
    const interval = setInterval(() => {
      setSeconds(prev => prev + 1); // functional updater!
    }, 1000);

    // Return cleanup — runs when component unmounts
    return () => clearInterval(interval);
  }, []); // empty array = set up once, clear on unmount

  return <p>Elapsed: {seconds}s</p>;
}
// Adding and removing window event listeners
function MouseTracker() {
  const [pos, setPos] = useState({ x: 0, y: 0 });

  useEffect(() => {
    const handleMove = (e) => {
      setPos({ x: e.clientX, y: e.clientY });
    };

    window.addEventListener('mousemove', handleMove);

    // Remove it when component unmounts — always!
    return () => {
      window.removeEventListener('mousemove', handleMove);
    };
  }, []);

  return <p>Mouse: {pos.x}, {pos.y}</p>;
}
// Cancelling a fetch request on cleanup
useEffect(() => {
  // AbortController lets you cancel in-flight requests
  const controller = new AbortController();

  fetch(`/api/users/${userId}`, {
    signal: controller.signal,
  })
    .then(res => res.json())
    .then(data => setUser(data))
    .catch(err => {
      // Ignore abort errors — they're expected
      if (err.name !== 'AbortError') setError(err);
    });

  // Cancel the request if userId changes or unmounts
  return () => controller.abort();
}, [userId]);
🧪 Experiment

  • Mount and unmount a component that has a timer. Check the console — does the timer stop?
  • Remove the cleanup return. Mount and unmount 5 times. Watch console — timers stack up. That's a memory leak.
04 Fetching Data — The Full Pattern pattern ▼

Data fetching is the most common useEffect use case. Here's the complete, production-ready pattern — with loading state, error handling, and cleanup.

// Minimal fetch pattern — Promise chain
function UserList() {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    fetch('https://jsonplaceholder.typicode.com/users')
      .then(res => {
        if (!res.ok) throw new Error('Network error');
        return res.json();
      })
      .then(data => {
        setUsers(data);
        setLoading(false);
      })
      .catch(err => {
        setError(err.message);
        setLoading(false);
      });
  }, []);

  if (loading) return <p>Loading...</p>;
  if (error) return <p>Error: {error}</p>;
  return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
}
// async/await — important: you can't make the effect itself async
useEffect(() => {
  // ❌ Can't do this: useEffect(async () => { ... }, [])
  // ✅ Define async function INSIDE, then call it

  const fetchUsers = async () => {
    try {
      setLoading(true);
      const res = await fetch('https://jsonplaceholder.typicode.com/users');
      if (!res.ok) throw new Error('Network error');
      const data = await res.json();
      setUsers(data);
    } catch (err) {
      setError(err.message);
    } finally {
      setLoading(false);
    }
  };

  fetchUsers(); // call it immediately
}, []);
// Refetch whenever a dependency (userId) changes
function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    setLoading(true); // reset loading on each fetch
    const controller = new AbortController();

    fetch(`https://jsonplaceholder.typicode.com/users/${userId}`, {
      signal: controller.signal,
    })
      .then(r => r.json())
      .then(data => { setUser(data); setLoading(false); })
      .catch(e => { if (e.name !== 'AbortError') setLoading(false); });

    return () => controller.abort(); // cleanup!
  }, [userId]); // re-fetch when userId changes

  if (loading) return <p>Loading...</p>;
  return <h2>{user?.name}</h2>;
}

05 Loading & Error States — The Complete UI Pattern pattern ▼

Every async operation has three possible states: loading, success, and error. Model all three explicitly in state — never assume success.

// The three-state pattern — always use all three
function DataComponent() {
  const [data, setData]       = useState(null);
  const [loading, setLoading] = useState(true);  // start as true!
  const [error, setError]     = useState(null);

  useEffect(() => {
    const load = async () => {
      try {
        setLoading(true);
        setError(null);    // clear previous error
        const res = await fetch('/api/data');
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        setData(await res.json());
      } catch (e) {
        setError(e.message);
      } finally {
        setLoading(false); // always stop loading
      }
    };
    load();
  }, []);

  // Early returns — handle each state
  if (loading) return <p className="loading">⏳ Loading...</p>;
  if (error)   return <p className="error">❌ Error: {error}</p>;
  if (!data)   return <p>No data found.</p>;

  return <div>{/* render data */}</div>;
}
🧪 Experiment
  • Fetch from a URL that doesn't exist. Does your error state catch it?
  • Add a "Retry" button that re-triggers the fetch. Hint: use a retry state counter in the dependency array.
  • Try fetching https://httpstat.us/500 — a URL that always returns a 500 error. Test your error handling.
06 Common Pitfalls — Bugs Everyone Hits pitfall ▼

These are the four most common useEffect bugs. Every React developer hits all of them. Know them now so you recognize them when they happen.

❌ PITFALL 1 — Infinite loop
// Setting state inside an effect with no deps / wrong deps
const [data, setData] = useState([]);

useEffect(() => {
  setData([...data, 'new item']); // sets data →
}, [data]); // → data changed → effect runs → sets data → ♾️
✅ Fix — use a ref or restructure logic
useEffect(() => {
  setData(['initial item']); // only set once on mount
}, []); // empty array breaks the loop
❌ PITFALL 2 — Async effect directly
// useEffect does NOT support async directly
useEffect(async () => {       // ← BAD
  const data = await fetchData();
}, []);
✅ Fix — define async inside, call it
useEffect(() => {
  const run = async () => {
    const data = await fetchData();
  };
  run();
}, []);
❌ PITFALL 3 — Stale closure (missing dep)
const [count, setCount] = useState(0);

useEffect(() => {
  const id = setInterval(() => {
    console.log(count); // always logs 0! stale closure
  }, 1000);
  return () => clearInterval(id);
}, []); // count is missing from deps
✅ Fix — use functional updater OR add dep
useEffect(() => {
  const id = setInterval(() => {
    setCount(prev => prev + 1); // always reads latest
  }, 1000);
  return () => clearInterval(id);
}, []); // now it's fine — no closure issue
❌ PITFALL 4 — Object/array deps that always change
// Objects are new references every render
useEffect(() => {
  fetchData(options);
}, [options]); // options = {} → new object every render = ♾️
✅ Fix — use primitives or useMemo
// Use primitive values as deps instead of the whole object
useEffect(() => {
  fetchData({ page: page, limit: limit });
}, [page, limit]); // primitives ✓
🧪 Experiment
  • Intentionally create an infinite loop with Pitfall 1. Open DevTools and watch the renders fly.
  • Create the stale closure bug with Pitfall 3. Add a console.log(count) inside setInterval and watch it log 0 forever.
  • Fix both using the techniques above.
07 Custom Hooks — Extracting Reusable Logic hook ▼

When you find yourself writing the same useState + useEffect pattern in multiple components, extract it into a custom hook. A custom hook is just a function that starts with use.

// Extract fetch logic into a reusable useFetch hook
// hooks/useFetch.js
import { useState, useEffect } from 'react';

function useFetch(url) {
  const [data, setData]       = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError]     = useState(null);

  useEffect(() => {
    const controller = new AbortController();

    const load = async () => {
      try {
        setLoading(true); setError(null);
        const res = await fetch(url, { signal: controller.signal });
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        setData(await res.json());
      } catch (e) {
        if (e.name !== 'AbortError') setError(e.message);
      } finally {
        setLoading(false);
      }
    };

    load();
    return () => controller.abort();
  }, [url]);

  return { data, loading, error };
}

// Now use it in any component — one line!
function UserList() {
  const { data, loading, error } = useFetch('https://jsonplaceholder.typicode.com/users');

  if (loading) return <p>Loading...</p>;
  if (error) return <p>Error: {error}</p>;
  return <ul>{data.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
}
// Another custom hook — useLocalStorage
function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    try {
      const stored = localStorage.getItem(key);
      return stored ? JSON.parse(stored) : initialValue;
    } catch { return initialValue; }
  });

  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);

  return [value, setValue];
}

// Use it like useState, but it persists to localStorage
const [theme, setTheme] = useLocalStorage('theme', 'dark');

  • Build a useWindowSize hook that returns { width, height } and updates on resize.
  • The naming rule is strict: custom hooks MUST start with use. Try naming one without it and see what React says.
08 Rules of Hooks — The Two Non-Negotiables concept ▼

React hooks have two strict rules enforced by the linter. Breaking them causes silent, hard-to-debug bugs. Understand why they exist and you'll never break them.

❌ RULE 1 — Never call hooks inside conditions or loops
function App() {
  if (someCondition) {
    const [count, setCount] = useState(0); // ❌ NEVER
  }

  for (let i = 0; i < 3; i++) {
    useEffect(() => {}); // ❌ NEVER
  }
}
✅ Always call hooks at the top level, unconditionally
function App() {
  // All hooks at the top, always called in the same order
  const [count, setCount] = useState(0);
  useEffect(() => { /* ... */ }, []);

  // Conditionals go INSIDE the hook, not around it
  useEffect(() => {
    if (someCondition) {
      // do something conditionally
    }
  }, [someCondition]);
}
❌ RULE 2 — Only call hooks from React functions
// Regular JS functions can't use hooks
function notAComponent() {
  const [x, setX] = useState(0); // ❌ Not a component or custom hook
}
✅ Hooks only in: React components OR custom hooks (use...)
// ✅ React function component
function MyComponent() {
  const [x, setX] = useState(0);
}

// ✅ Custom hook (starts with "use")
function useMyHook() {
  const [x, setX] = useState(0);
}
💡 Why the order rule exists

React identifies hooks by their call order, not by name. It tracks "1st hook, 2nd hook, 3rd hook..." on every render. If you put a hook inside an if statement, it might be skipped on the next render — breaking React's internal count and causing wrong values to map to the wrong hooks.

🧪 Experiment
  • Install the eslint-plugin-react-hooks plugin (it comes with Vite's React template). It enforces these rules automatically.
  • Try putting a useState inside an if block. The linter will flag it red before you even run it.
  • Look at your Day 1 and Day 2 code — are you already following these rules? You probably are without knowing it.
